# 기획서 — random_scene_menu (메인 메뉴 UI 리디자인)

> 결정 도우미 앱 메인 메뉴 / RandomScene 진입 화면
> 작성: game-designer 단계 (구현 전). 코드 없음 — 본 문서는 gameplay-programmer 의 구현 입력.

---

## § 헤더 (한눈 요약)

- **목표**: RandomScene 의 모드 진입 메뉴를 가시성·심미성·확장성(10+ 항목) 을 갖춘 **세로 스크롤 카드 리스트**로 리디자인한다.
- **검증 가설**: "과대한 셀(600×300)과 위계·대비 없는 흰 텍스트로 인해 어디가 눌리는 항목인지 즉시 안 읽히던 메뉴를, 적정 크기(168) 카드 + 아이콘/제목/설명 위계 + 다음 항목 peek 가 있는 세로 스크롤 리스트로 바꾸면 가시성·심미성이 개선된다. (부수적으로 일부 화면에서 항목이 화면 밖으로 잘려 도달 불가였던 문제도 스크롤 도입으로 해소된다.)"
- **현재 단계 범위 적합성**: 범위 내. 이 앱은 게임 컨셉서가 없는 유틸 앱(운영/유지보수 단계). 사용자 요구(가시성+심미성)를 직접 입력으로 매핑. 메뉴는 기존 기능의 진입점이므로 신규 콘텐츠가 아닌 UX 개선.
- **핵심 메커니즘**: 세로 1열 카드 리스트(`CHPoolingScrollView`). 카드 = 아이콘 + 제목 + 한 줄 설명. 다음 항목이 살짝 보이도록(peek) 잘려 "더 있음"을 신호. 10+ 항목은 풀링으로 처리.

## 1. 가시성 문제 진단 (현재 왜 안 보이는가)

> 사용자 표현: "스크롤 형태인데 잘 안 보인다." → **씬 분석 결과 실제로는 스크롤이 없다.** 정확한 원인은 아래.

### 1.1 씬 실측 (`Assets/Scenes/RandomScene.unity`)

| 항목 | 실측값 | 출처 |
|---|---|---|
| 메뉴 컨테이너 | `MenuGroup` (fileID 1574888588) | 부모 = `RandomScene` 루트(886570682) → Canvas(1954582237) |
| `MenuGroup` 레이아웃 | **LayoutGroup 컴포넌트 없음** (RectTransform 만) | 컴포넌트 1개(`RectTransform`)뿐 |
| `MenuGroup` 크기/앵커 | sizeDelta 100×100, 앵커 (0.5,0.5) 중앙 고정 | RectTransform |
| 메뉴 버튼 4개 위치 | y = 0 / −350 / −700 / −1050 (절대 배치) | 각 버튼 anchoredPosition |
| 버튼 1개 크기 | **600 × 300 px** | 각 버튼 sizeDelta |
| ScrollRect 유무 | **메뉴에 없음** (씬의 "Scroll View" 는 서브씬 입력 영역 소속, 메뉴 아님) | 부모 체인 검증 |
| Canvas Scaler | ref 1280×720, ScaleWithScreenSize, **MatchWidthOrHeight = 0 (폭 매치)** | Canvas 컴포넌트 |
| 화면 방향 | **세로 고정 (Portrait)** | ProjectSettings `defaultScreenOrientation: 0` |

### 1.2 원인 (3중 결함)

> **원인을 보편성 순으로 정렬.** B·C 는 모든 디바이스에서 항상 발생(체감 핵심), A 는 짧은 화면일수록 치명.

**원인 B — 과대한 셀 크기 (모든 화면에서 발생).** 버튼 600×300 은 폭 1280 캔버스에서 폭의 47%, 높이는 9:16 캔버스(2276)의 13%. 한 항목이 지나치게 커서 한 화면에 **4~6개만** 들어오고, 10+ 로 늘면 화면 밖 비율이 폭증한다. 어느 디바이스에서나 항상 발생하는 1차 원인.

**원인 C — 시각 위계·대비 부족 (모든 화면에서 발생).** 메뉴 버튼 라벨/배경 색이 대부분 흰색(`m_Color 1,1,1,1`)으로, 다크 배경(`#262626`) 위에서 카드 간 구분·아이콘·설명이 없어 "어디가 눌리는 버튼인지" 즉시 안 읽힌다. 타이틀과 항목의 위계도 없다. 사용자 체감의 핵심.

**원인 A — 스크롤 부재 + 화면 밖 오버플로 (짧은 화면일수록 치명).** 메뉴 버튼 4개가 레이아웃 그룹 없이 절대 좌표로 y=0~−1050(세로 1050px 범위)에 흩뿌려져 있고, 부모 `MenuGroup` 은 100×100 중앙 고정이라 클리핑/스크롤이 없다. 세로 캔버스에서 폭 매치(1280 기준)이므로 디바이스 종횡비에 따라 캔버스 높이가 달라진다 — 검산 (셀 하단 extent = 중심 y − 높이/2, 버튼4 = −1050 − 150 = **−1200**):

| 디바이스 종횡비 | 캔버스 높이(유닛) | 중앙 기준 하단 가시 한계 | 버튼4 하단(−1200) 가시성 |
|---|---|---|---|
| 9:16 (1080×1920) | 1280 × 16/9 = **2276** | −1138 | **하단 62px 잘림** (−1200 < −1138), 배너가 더 가림 |
| 3:4 (768×1024, 태블릿) | 1280 × 4/3 = **1707** | −853 | **거의 전부 화면 밖** → 도달 불가 |
| 19.5:9 (요즘 폰) | 1280 × 19.5/9 = **2773** | −1387 | 들어옴(여유) |

→ 19.5:9 같은 긴 화면에서만 4개가 다 들어오고, **9:16 에서도 4번째가 하단부터 잘리며, 3:4 에선 거의 화면 밖**이다. 스크롤이 없어 끌어올 수도 없다. 항목이 하단으로 쏠려 상단 절반이 비는 불균형도 동반된다.

### 1.3 해결 방향 (진단 → 처방 매핑)

| 원인 | 처방 | §참조 |
|---|---|---|
| B 과대 셀 | 셀 높이 300→**168**, 폭 풀폭(좌우 여백 후) — 한 화면 다수 + peek | §3, §4 |
| C 대비/위계 | 카드 면(패널) + 아이콘 + 제목/설명 2단 + 상단 타이틀 위계 | §5 |
| A 스크롤 부재 | `CHPoolingScrollView` 세로 리스트로 교체 — 모든 항목 스크롤 도달 + 다음 항목 peek 로 "더 있음" 신호 | §2, §6 |

## 2. 핵심 결정 — 세로(상하) 스크롤 vs 가로(좌우) 스크롤

### 2.1 비교표

| 기준 | 세로(상하) 스크롤 ✅ 추천 | 가로(좌우) 스크롤 |
|---|---|---|
| **가시성(항목 수 인지)** | 다음 항목이 위→아래로 잘려 보여 "더 있음"이 직관적 | 옆 항목 일부 노출 가능하나, 전체 개수 감 잡기 어려움 |
| **확장성(10+ 항목)** | 무제한 — 길이만 늘어남. 풀링과 자연 결합 | 길어질수록 가로 스와이프 횟수↑, "끝이 어디?" 불안 |
| **썸 리치(한손 조작)** | 세로 스와이프 = 모바일 가장 자연스러운 제스처 | 전체화면 가로 스와이프는 OS 뒤로가기 스와이프와 충돌 위험 |
| **모바일 관용 패턴** | 설정·앱서랍·리스트의 보편 패턴(전체 탐색형) | 캐러셀 = 큐레이션된 소수(3~6개) 강조용 패턴 |
| **셀 크기/터치 타깃** | 풀폭 카드 → 큰 터치 타깃 + 아이콘+제목+설명 여유 | 좁은 카드 강제 or 1개씩 페이징 → 설명 공간 부족 |
| **심미성** | 카드 리스트 = 정돈된 인상, 위계 주기 쉬움 | 화려하나 정보 밀도 낮고 "탐색"보다 "전시" 느낌 |

### 2.2 추천 — **세로 스크롤**

**근거**: 이 메뉴는 *큐레이션된 소수*가 아니라 **전부 훑어 고르는 전체 목록**이며 10~15종으로 성장한다(아래 §6). 가로 캐러셀은 "오늘의 추천 3선" 같은 소수 강조 패턴이고, 전체 탐색에는 세로 리스트가 모바일 보편 관용이다. 사용자의 핵심 불만("개수·항목이 안 보인다")은 세로 리스트의 peek(다음 항목 살짝 노출)로 정확히 해소된다. 가로는 오히려 전체 개수를 더 숨긴다.

> **승인 게이트**: 위 비교를 근거로 game-designer 는 **세로**를 단일 추천한다. 사용자가 가로를 원하면 §3~§5 의 셀 치수·peek 규칙을 가로축 기준으로 재산정해야 하며(셀 폭/페이징 결정 추가 필요), 그 경우 "사용자 선택 필요" 로 본 기획서를 재작업한다.

## 3. 메뉴 셀(카드) 디자인

> 모든 치수는 **Canvas ref 1280×720, 폭 매치** 기준 캔버스 유닛(px). 폭 매치이므로 폭 1280 은 모든 세로 디바이스에서 고정 → 폭 기준 수치는 디바이스 불변.

### 3.1 셀 레이아웃

```
┌───────────────────────────────────────────────┐  ← 카드 (1180 × 168), 좌우 여백 50씩
│  ┌────────┐                                    │
│  │ 아이콘 │   동전 던지기              ›        │  제목 (CHText, 44px, 흰색)
│  │ 96×96  │   앞/뒤 빠른 양자택일      (셰브런) │  설명 (CHText, 26px, #b8b8c0)
```

|---|---|---|
| 카드 외곽 | 폭 1180 × 높이 **168** | 폭=1280−(좌우 여백 50×2). 높이 168 → 9:16 화면 약 10개 노출 + peek(§4.2 검산) |

| 설명(CHText) | 폰트 26px, `#b8b8c0`, 제목 아래 6 간격 | 2차 위계. 한 줄(말줄임) |

### 3.2 상태별 비주얼

| 상태 | 카드 면 | 테두리 | 비고 |

## 4. 레이아웃 / 간격 / 한 화면 표시 개수

### 4.1 화면 구성 (세로, 위→아래)

```
상단 타이틀 영역      높이 220  (앱 타이틀 + 부제)
리스트 영역(스크롤)    상단 220 ~ 하단 배너 위까지
하단 광고 배너         Admob (기존 ShowBanner) — 리스트가 가리지 않게 하단 여백 확보
```

| 항목 | 값 | 근거 |
|---|---|---|
| 카드 높이 | 168 | §3 |
| 카드 간 세로 간격 | 24 | 카드 구분 + 과밀 방지. 단위행 = 168+24 = **192** |
| 리스트 좌우 여백 | 50 | §3 폭 검산과 일치 |
| 리스트 상단 시작 | 캔버스 상단에서 220 (타이틀 아래) | 타이틀 위계 확보 |
| 리스트 하단 패딩 | 120 (배너/세이프영역 + 마지막 카드 호흡) | 마지막 항목이 배너에 안 붙음 |

### 4.2 한 화면 표시 개수 검산 (9:16, 캔버스 높이 2276)

```
가용 리스트 높이 = 2276 − 220(타이틀) − 120(하단패딩) = 1936
단위행 = 192 (카드168 + 간격24)
표시 개수 = 1936 / 192 = 10.08행
```

→ 9:16 폰에서 **약 10개**가 한 화면에 들어온다. 3:4 화면(높이 1707): (1707−220−120)/192 = **7.1개**. 어느 화면에서도 마지막 항목이 잘려 보이면 peek 신호가 살아 있고, 더 많아지면 스크롤로 전부 도달 가능(원인 A 해소).

> **peek 보장 규칙**: 항목 수 × 192 가 가용 높이를 초과하면 마지막 보이는 카드가 자연히 절반 잘린다. 항목 수가 적어(예 4개) 화면을 다 못 채우면 스크롤 비활성 + 리스트를 **상단 정렬**(중앙 쏠림 금지 — 원인 A의 불균형 방지).

## 5. 비주얼 (팔레트 · 위계 · 아이콘)

### 5.1 색 팔레트 (현재 앱 톤 — 씬/기존 목업 실측 기반)

| 토큰 | 값 | 출처/용도 |
|---|---|---|
| 배경 | `#262626` | 기존 목업 `--bg` (앱 다크 배경) |
| 카드 면 | `#34343c` | 배경 대비 위계용 (씬 다크 패널 `0.32,0.32,0.36`≈`#525258` 계열의 더 어두운 톤) |
| 라인/아웃라인 | `#ffffff` (저투명) | 기존 목업 `--line` (흰 아웃라인 관용) |
| 액센트(골드) | `#ffd64d` | 기존 목업 `--gold` — 타이틀 강조·아이콘 틴트 포인트 |
| 제목 텍스트 | `#ffffff` | 1차 위계 |
| 설명 텍스트 | `#b8b8c0` | 2차 위계(저대비 보조) |
| 셰브런 | `#6f6f78` | 약한 어포던스 |

### 5.2 시각 위계 (타이틀 vs 항목)

```
앱 타이틀:  폰트 56px, 흰색, 가운데 또는 좌정렬     ← 최상위
부제:       폰트 26px, #b8b8c0  "무엇을 정해볼까요?" ← 보조
카드 제목:  폰트 44px, 흰색                          ← 항목 1차
카드 설명:  폰트 26px, #b8b8c0                        ← 항목 2차
```

타이틀(56) > 카드 제목(44) > 설명/부제(26) 의 3단 위계로, 현재 "전부 같은 흰 텍스트라 위계 없음"(원인 C) 을 해소.

### 5.3 모드별 아이콘 매핑 (Dark UI 팩 활용)

> 아이콘은 `Assets/Dark UI/Free` 와 `Assets/Dark UI/New Icons` 의 흰색 아이콘을 **Addressable 로 등록**(Rule 04). 흰 아이콘 + 카드별 골드/뉴트럴 틴트로 통일감. 각 모드 셀 데이터에 아이콘 키를 부여.

**이번 빌드에 실제로 들어가는 4종** (현재 `ERouletteMenu` 구현 항목 — 본 리디자인의 실제 구현 대상):

| 모드(enum) | 권장 아이콘(Dark UI 의미 매핑) | 제목 | 설명 |
|---|---|---|---|

## 6. 10+ 확장 시 동작

- 현재 `docs/design/` 에 **10종 모드 기획서**(dice, yes_no, ladder, lottery, team_split, rps, menu_picker, order_shuffle, random_number, coin_flip) 존재 → 메뉴는 **현재 4종 → 10~15 항목**으로 성장 예정. 본 리디자인은 이를 전제로 설계하되, **이번 구현은 기존 4종을 카드 리스트로 재구성**하는 것까지가 범위(신규 모드는 각 모드 기획서 구현 시 추가).
- **스크롤 길이**: 항목 수 × 192(단위행)만큼 Content 높이가 늘어난다. 15개면 Content 높이 = 15×192 − 24(마지막 간격) = 2856 → 9:16 화면(가용 1936)을 초과하므로 자연 스크롤.
- **풀링**: `CHPoolingScrollView<TItem,TData>` 가 화면 표시분 + 버퍼만 인스턴스화 → 항목이 50개로 늘어도 셀 GameObject 는 화면분(~10) + 버퍼만 유지. 항목 증가에 따른 메모리/생성 비용 선형 증가 없음.
- **데이터 주도**: 메뉴 항목은 코드 하드코딩이 아니라 **셀 데이터 리스트**(아이콘 키 + 제목 stringID + 설명 stringID + 진입 enum)로 구성 → 모드 추가 = 데이터 1행 추가 + enum 1값 추가 + 서브씬 와이어링. 메뉴 레이아웃 코드는 불변.

## 7. 구현 요청사항 (gameplay-programmer 용)

> 본 § 는 명세만 한다. 코드·ChvjPackage API 호출 방식은 gameplay-programmer 판단.

### 7.1 Enum 값

- `CommonEnum.ERouletteMenu` 에 신규 모드 enum 값 추가 — 현재 `{ Menu, RandomNumber, RandomFood, CustomRandom, CoinFlip }`. 10종 모드 도입 시 각 모드 값 추가(예: `Dice`, `YesNo`, `Ladder`, `Lottery`, `TeamSplit`, `Rps`, `MenuPicker`, `OrderShuffle`). **본 메뉴 리디자인 자체는 enum 신규 추가 불필요** — 기존 항목을 카드 리스트로 재구성하는 것이 범위. (모드 추가는 각 모드 기획서 구현 시.)
- 아이콘 에셋 키 enum: 모드별 아이콘을 Addressable 로 로드하므로 **아이콘 키 enum 신설 권장** (예 `EMenuIcon { Coin, Dice, ... }`, 값명 = 아이콘 에셋 파일명, Rule 03 §2). 또는 셀 데이터에 아이콘 Addressable 주소 문자열을 두는 방식 중 **enum 키 방식** 으로 통일(하드코딩 문자열 금지, Rule 03 §2).

### 7.2 Interface

- 신규 인터페이스 불필요. 기존 `IRandomSceneAccess.ShowScene(ERouletteMenu)` 진입 경로를 그대로 사용 — 카드 탭 → `ShowScene(menu)` 호출. (메뉴 카드는 기존 `_liMenu` 버튼 바인딩을 대체.)

### 7.3 에셋 키 (Rule 03 §2 / Rule 04)

- 메뉴 셀 프리팹: `MenuCardCell.prefab` (재사용 단위) → `Assets/AddressableResource/Prefab/` (Rule 04 — 재사용 프리팹은 Prefab 폴더).
- 메뉴 패널/스크롤뷰: `RandomScene.unity` 내 정적 배치(서브씬 선례대로 씬 내 GameObject).
- 아이콘 스프라이트: `Assets/AddressableResource/Sprite/` (Sprite 폴더 신설, Rule 04). 파일명 = 아이콘 enum 값명.

### 7.4 SO / 데이터 스키마 (셀 데이터)

`CHPoolingScrollView<MenuCardCell, MenuCardData>` — `MenuCardData` 필드:

| 필드 | 타입 | 의미 |
|---|---|---|
| `menu` | `CommonEnum.ERouletteMenu` | 탭 시 진입할 모드 |
| `iconKey` | 아이콘 enum (`EMenuIcon` 등) | 카드 아이콘 |
| `titleStringID` | int | 제목 String.json stringID |
| `descStringID` | int | 설명 String.json stringID |

- 표시 문자열은 모두 **String.json stringID** 경유(기존 정책 — coin_flip 기획서 §7 동일). 제목/설명 신규 stringID 는 기존 사용 번호 이후로 순차 할당(예 coin_flip 이 142~149 사용 → 그 이후).

### 7.5 ChvjPackage / Rule 03 §3 제약 (BuildModalPopup 패턴)

> 스크롤 구현은 **반드시 Rule 03 §3 의 3-class 분리 + 정적 배치** 를 따른다. 동적 GameObject 생성 금지.

| 클래스 | 책임 |
|---|---|
| `MenuPanel`(또는 RandomScene 내 컨테이너) | `[SerializeField] _scrollView` 인스펙터 참조. 셀 데이터 리스트 구성 → `_scrollView.SetItemList(data)` |
| `MenuCardPoolingScrollView : CHPoolingScrollView<MenuCardCell, MenuCardData>` | `InitItem(cell, data, index)` / `InitPoolingObject` 오버라이드. `_origin` 인스펙터 |
| `MenuCardCell : MonoBehaviour` | `[SerializeField]` 자식(`_icon Image`, `_title CHText`, `_desc CHText`, `_button CHButton`). `Bind(data)` / `OnEnable` 풀 재사용 리셋 |

- 텍스트 = **CHText** (Jua 폰트), 버튼/탭 = **CHButton**, 정적 라벨(타이틀·부제)도 CHText (Rule 03 §3 — 정적 라벨 예외 없음).
- Content 에 **VerticalLayoutGroup** + 셀 간격 24(§4.1), 좌우 패딩 50. ContentSizeFitter 또는 CHPoolingScrollView 의 Content 크기 산정 사용.
- 셀 `_origin` 은 Content 자식으로 정적 배치(prototype). 코드 `Instantiate`/`new GameObject` 금지.
- 클릭 사운드: 기존 `CHButton.ClickSoundHook` 정책 그대로(EAudio.Click).

### 7.6 기존 RandomScene.cs 영향

- 현재 `_liMenu`(버튼 4개 수동 바인딩) → 데이터 주도 리스트로 대체. `SetMenuButton()` 의 foreach 바인딩은 셀의 `Bind` 내 `_button.OnClick` 으로 이동.
- `ShowScene` switch / `liMainSceneObj` 토글 로직은 **불변**(메뉴 화면 = 스크롤뷰를 포함한 GameObject 들이 `liMainSceneObj` 에 들어가도록 재구성).
- 기존 절대배치 메뉴 버튼 4개(`CoinMenuButton` 등) 와 `MenuGroup` 의 흩뿌린 배치는 제거 → 스크롤뷰로 교체.

## 8. 엣지 케이스 / 구현 메모

- 항목 수가 화면보다 적을 때(현재 4~5개): 스크롤 비활성, 리스트 **상단 정렬**(중앙 쏠림 금지 — 원인 A 재발 방지). 카드들이 타이틀 바로 아래부터 채워짐.
- 하단 Admob 배너가 마지막 카드를 가리지 않도록 리스트 하단 패딩 120 확보(§4.1).
- 서브씬 진입 후 메뉴 복귀 시(`ShowScene(Menu)`) 스크롤 위치는 **상단으로 리셋**(매번 처음부터 보이게).
- 풀 재사용 시 이전 카드의 아이콘/텍스트 잔존 방지 — `MenuCardCell.OnEnable` 또는 `Bind` 에서 전 상태 리셋(Rule 03 §4 State Reset).
- 긴 제목/설명은 1줄 말줄임(...) — 카드 높이 168 고정 유지.
